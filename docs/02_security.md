# TaskFlow — безопасность приложения и базы данных

Документ описывает модель угроз, реализованные меры защиты и рекомендации для
промышленной эксплуатации. Проект учебный, но конфигурация приближена к реальной.

---

## 1. Модель угроз (STRIDE)

| Угроза                     | Пример                        | Мера в проекте                                                                         |
| -------------------------- | ----------------------------- | -------------------------------------------------------------------------------------- |
| **S**poofing               | Кража/подделка JWT            | Подпись HS256, срок жизни, проверка схемы payload, `JWT_SECRET` ≥ 16 символов          |
| **T**ampering              | Изменение чужой задачи        | Проверка владельца проекта в сервисе, 403                                              |
| **R**epudiation            | Отрицание смены статуса       | Таблица `task_status_history`, `changed_by`, `changed_at`                              |
| **I**nformation disclosure | Доступ к `password_hash`      | Пароли не возвращаются API; `report_user` не имеет прав на `password_hash`             |
| **D**enial of service      | Тяжёлые запросы/брутфорс      | Лимит `limit ≤ 100`, таймауты внешних API, индексы; rate limit — рекомендация для prod |
| **E**levation of privilege | USER выполняет действия ADMIN | Роль берётся только из проверенного JWT, RBAC в сервисах                               |

---

## 2. Аутентификация

- Пароли хранятся только в виде bcrypt-хеша (`bcryptjs`, 10 раундов, соль автоматическая).
- Пароль никогда не логируется и не возвращается клиенту.
- JWT подписывается `JWT_SECRET` (HS256), payload:

```json
{ "sub": "1", "id": 1, "username": "ivan", "role": "USER", "iat": 1760000000, "exp": 1760086400 }
```

- `authMiddleware` проверяет подпись, срок действия и **структуру** payload через zod.
- Срок жизни задаётся `JWT_EXPIRES_IN` (по умолчанию `1d`).
- Неверный/просроченный токен → `401`. Токен хранится в `localStorage` SPA; при `401`
  клиент удаляет его и показывает форму входа.
- Единый ответ при неверном email или пароле — защита от перечисления пользователей.
- Заблокированный пользователь не может войти (`403`) и быть назначенным исполнителем (`403`).

**Рекомендации для production:** httpOnly + Secure + SameSite cookie вместо
`localStorage`, refresh-токены, ротация ключей, MFA для администраторов, rate limiting
на `/api/login` и `/api/register`.

## 3. Авторизация

| Действие               | USER                 | ADMIN          |
| ---------------------- | -------------------- | -------------- |
| Список задач           | только свои проекты  | все проекты    |
| Создание задачи        | только в свой проект | в любой проект |
| Смена статуса          | только свои задачи   | любые          |
| Назначение исполнителя | только свои задачи   | любые          |
| Чужие проекты          | `403`                | разрешено      |

Проверки выполняются в `task.service.ts` **до** записи в БД. Роль берётся из
проверенного JWT, а не из тела запроса. `req.user` типизирован через
`types/express.d.ts`.

---

## 4. Валидация входных данных

- Все тела запросов проходят zod-схемы в `middlewares/validate.middleware.ts`.
- Query/params валидируются через `parseOrThrow` (`page`, `limit`, `status`, `:id`, `projectId`).
- Ограничения: `title` 1–200, `description` ≤ 2000, `priority` 1–5, пароль ≥ 8,
  `username` 3–50, корректный email, `limit` 1–100.
- `express.json({ limit: '1mb' })` ограничивает размер тела.
- Битый JSON → `400 Invalid JSON payload`.
- Ответ валидации не раскрывает внутренние детали: `{ error, issues[] }`.

## 5. Защита от SQL-инъекций

- Приложение работает через Prisma 7 и драйвер `pg`; значения передаются
  параметризованно, конкатенация пользовательских строк в SQL отсутствует.
- В SQL-скриптах динамически формируется только имя БД в `00_init.sql` — через
  `format('%I', ...)` и `quote_ident`, что исключает инъекцию.
- Функции БД принимают типизированные параметры (`INT`, `"TaskStatus"`), а не текст SQL.
- Роль приложения не имеет прав `SUPERUSER`, `CREATEDB`, `CREATEROLE`.
- `search_path` фиксируется (`lib, public`), схема `public` не используется для объектов.

## 6. Секреты и конфигурация

- Секреты хранятся в `.env` (не коммитится), в репозитории — только `.env.example`
  и `.env.test.example`.
- `.gitignore` исключает `.env`, `*.log`, `backups/`, `*.dump`, `*.backup`.
- `config/env.ts` валидирует окружение при старте (fail fast): без `DATABASE_URL`
  и `JWT_SECRET` приложение не запустится.
- В примерах — только фиктивные значения; реальные ключи выдаются отдельно.
- Для production: секрет-менеджер (Vault/KMS), ротация, разные ключи по средам.

## 7. Роли и привилегии PostgreSQL

Скрипт `db/06_roles.sql` реализует принцип минимальных привилегий:

| Роль                  | Права                                                                                                            |
| --------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `taskflow` (владелец) | полный доступ к схеме `lib`                                                                                      |
| `app_user`            | `SELECT, INSERT, UPDATE, DELETE` на таблицы, `USAGE, SELECT` на последовательности                               |
| `report_user`         | только `SELECT` на `tasks`, `projects`, представления и аудит; на `users` — по колонкам, **без** `password_hash` |

Дополнительно:

- `REVOKE ALL ON SCHEMA lib FROM PUBLIC`;
- отзыв прав на схему `public`;
- `ALTER DEFAULT PRIVILEGES` не выдаёт лишних прав;
- проверка в `db/08_checks.sql`: `has_table_privilege('report_user','lib.tasks','SELECT') = true`,
  `INSERT = false`;
- фактическая проверка: `INSERT` от `report_user` завершается `permission denied`.

## 8. Сеть, TLS и pg_hba

`postgres/pg_hba.conf`:

- `local` — только Unix-сокет, `peer` (Linux);
- `hostssl` — подключения только по TLS с `scram-sha-256`;
- `host` — резервная строка для локальной разработки (в production удалить);
- порядок правил: сначала `hostssl`, затем `host`; запрещающая строка `all all all reject`.

`postgres/postgresql.conf`:

- `password_encryption = scram-sha-256` (не md5);
- `listen_addresses = '*'` только внутри контейнера/закрытой сети;
- `log_connections`, `log_disconnections`, `log_min_duration_statement = 500`;
- `ssl = off` в учебном контуре; для production включить `ssl = on`,
  `ssl_cert_file`, `ssl_key_file` и перейти на `hostssl`.

`docker-compose.yml` публикует порт только на `127.0.0.1` и использует именованный
volume; пароль передаётся через переменную окружения.

**Рекомендации:** firewall/security group, VPN для админ-доступа, отдельная сеть
приложений и БД, запрет прямого доступа к 5432 из интернета.

## 9. Аудит и логирование

- Приложение: JSON-логи в `server/logs/app.log` (timestamp, level, message, meta),
  HTTP-доступ через morgan.
- Ошибки с стеком не отдаются клиенту — только `Internal server error`.
- БД: триггер `trg_tasks_status_history` пишет каждую смену статуса с `current_user`
  и временем; история недоступна для изменения роли `report_user`.
- PostgreSQL: `log_connections`, `log_disconnections`, `log_checkpoints`,
  `log_min_duration_statement`.
- Секреты и пароли не попадают в логи; тело запроса не логируется.

**Рекомендации:** централизованный сбор логов (ELK/Loki), алерты на 5xx и всплеск 401,
ротация логов, immutable-хранилище для аудита.

---

## 10. Резервное копирование и восстановление

- `backup/backup.sh` / `backup/backup.ps1` — `pg_dump -Fc -Z 6` (custom format),
  имя файла с UTC-таймстампом, проверка размера, retention.
- `backup/restore.sh` / `backup/restore.ps1` — `pg_restore --clean --if-exists`,
  восстановление в отдельную БД, затем проверка количества строк.
- Рекомендуемая схема 3-2-1: три копии, два носителя, одна вне площадки.
- Шифрование: `gpg`/`age` или шифрованный bucket; ключи отдельно от дампов.
- Регулярная учебная проверка восстановления (restore drill) — минимум раз в квартал.
- Для production: WAL-архивирование и PITR (`archive_mode = on`, `pg_basebackup`).

- [ ] Включить rate limiting на `/api/login` и `/api/register`.
- [ ] Перевести JWT в httpOnly-cookie, добавить refresh и CSRF-защиту.
- [ ] Настроить `npm audit`/Dependabot и обновление базовых образов.
- [ ] Включить WAL-архивирование и проверить восстановление на копии.
- [ ] Настроить алерты на 5xx, 401-аномалии и ошибки подключения к БД.
- [ ] Ограничить доступ к `report_user` и ротировать его пароль.
- [ ] Проверить, что `.env`, дампы и логи исключены из репозитория.
