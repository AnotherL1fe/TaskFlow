# TaskFlow — анализ предметной области и проектирование

Документ фиксирует требования, модель данных и архитектурные решения учебного проекта
**TaskFlow**, разработанного в рамках ПМ.02 «Осуществление интеграции программных модулей»
и ПМ.11 «Разработка, администрирование и защита баз данных».

---

## 1. Цель и границы проекта

**Цель:** создать веб-приложение для управления задачами и проектами с разграничением
доступа, контролем сроков, интеграциями с внешними сервисами и полноценным контуром
администрирования PostgreSQL.

**Входит в границы:**

- регистрация и аутентификация пользователей по JWT;
- проекты и задачи, назначение исполнителей, приоритеты, дедлайны;
- статусная модель задачи с проверкой допустимых переходов;
- выборка просроченных задач и пагинация списка;
- уведомления (Telegram / консоль) и получение погоды через внешний API;
- React SPA для работы с задачами;
- автоматические тесты API и интеграций, покрытие бизнес-логики;
- SQL-скрипты создания БД, роли, представления, функции, триггеры, проверки;
- резервное копирование/восстановление, настройки PostgreSQL и Docker Compose.

**Не входит:** мобильное приложение, полнотекстовый поиск, загрузка файлов, биллинг,
интеграция с календарями, мультиязычность интерфейса, горизонтальное шардирование.

## 2. Заинтересованные стороны и роли

| Роль        | Описание                        | Права                                                            |
| ----------- | ------------------------------- | ---------------------------------------------------------------- |
| Гость       | Не аутентифицирован             | `/health`, регистрация, вход                                     |
| USER        | Зарегистрированный пользователь | CRUD задач своего проекта, смена статуса, назначение исполнителя |
| ADMIN       | Администратор системы           | То же + доступ к задачам любых проектов                          |
| blocked     | Заблокированный пользователь    | Вход запрещён (403), назначение исполнителем запрещено           |
| report_user | Роль БД для отчётности          | Только `SELECT` на таблицы/представления, без изменения данных   |
| DBA         | Администратор PostgreSQL        | Управление ролями, бэкапы, мониторинг, проверки                  |

Бизнес-правило владения: проект принадлежит одному пользователю (`projects.owner_id`).
Пользователь видит и изменяет задачи только тех проектов, которыми владеет; `ADMIN`
видит все проекты. Задача может быть назначена только активному (не заблокированному)
пользователю.

## 4. Сценарии использования

### UC-01. Регистрация

1. Гость отправляет `POST /api/register`.
2. Сервер валидирует поля (zod), проверяет уникальность.
3. Пароль хешируется bcrypt (10 раундов), создаётся пользователь с ролью `USER`.
4. Возвращается `201` с JWT и публичными полями пользователя.

**Альтернативы:** занятый логин/email → `400`; невалидные поля → `400` с массивом `issues`.

### UC-02. Вход

1. `POST /api/login` с email и паролем.
2. Поиск пользователя, сравнение bcrypt-хеша.
3. Проверка `is_blocked`; при блокировке → `403`.
4. Успех → `200` + JWT (срок жизни из `JWT_EXPIRES_IN`).

### UC-03. Создание задачи

1. Аутентифицированный пользователь отправляет `POST /api/tasks`.
2. Middleware проверяет Bearer-токен и структуру payload.
3. Контроллер валидирует тело, сервис проверяет проект и исполнителя.
4. Задача сохраняется со статусом `NEW` и приоритетом по умолчанию `3`.
5. Вызывается Observer-хук уведомления; ошибка доставки логируется, но не влияет на ответ.
6. Возвращается `201` и созданная задача.

### UC-04. Смена статуса

1. `PATCH /api/tasks/:id/status` с `{ "status": "DONE" }`.
2. Проверяются права на проект и допустимость перехода.
3. Задача обновляется, `updated_at` меняется.
4. Возвращается `200` с новым состоянием.

Недопустимый переход (например, `DONE → NEW`) → `400`.

### UC-05. Просроченные задачи

`GET /api/tasks/overdue?projectId=1` возвращает задачи проекта, у которых дедлайн в прошлом
и статус не `DONE`, отсортированные по дедлайну.

### UC-06. Работа в SPA

Пользователь входит, видит список задач, фильтрует по статусу, создаёт задачу и переводит
её в работу/завершает. При `401` токен удаляется и показывается форма входа.

### UC-07. Отчётность БД

Аналитик подключается ролью `report_user`, выполняет `SELECT` по представлениям
`v_task_details`, `v_project_stats`, `v_overdue_tasks`; изменение данных запрещено.

### UC-08. Резервное копирование

DBA запускает `backup/backup.ps1` (Windows) или `backup/backup.sh` (Linux), получает
custom-дамп, проверяет его через `pg_restore --list`, восстанавливает в отдельную БД.

## 5. Модель данных

### 5.1. ER-диаграмма

```
┌────────────────────┐          ┌────────────────────┐
│       users        │          │      projects      │
├────────────────────┤          ├────────────────────┤
│ id            PK   │◄────┐    │ id            PK   │
│ username      UQ   │     │    │ title              │
│ email         UQ   │     │    │ owner_id      FK ──┼──► users.id
│ password_hash      │     │    │ is_archived        │
│ role (ADMIN/USER)  │     │    └─────────┬──────────┘
│ is_blocked         │     │              │ 1
│ created_at         │     │              │
└─────────┬──────────┘     │              │ N
          │ 1              │    ┌─────────▼──────────┐
          │                │    │       tasks        │
          │                │    ├────────────────────┤
          │                └────┤ id            PK   │
          │  assignee_id        │ title              │
          └─────────────────────┤ description        │
                                │ status             │
                                │ priority           │
                                │ deadline           │
                                │ project_id    FK   │
                                │ created_at         │
                                │ updated_at         │
                                └─────────┬──────────┘
                                          │ 1
                                          │ N
                                ┌─────────▼──────────────┐
                                │ task_status_history    │
                                ├────────────────────────┤
                                │ id                 PK  │
                                │ task_id            FK  │
                                │ old_status             │
                                │ new_status             │
                                │ changed_by             │
                                │ changed_at             │
                                └────────────────────────┘
```

### 5.2. Таблицы

| Таблица                   | Назначение           | Ключевые ограничения                                                                      |
| ------------------------- | -------------------- | ----------------------------------------------------------------------------------------- |
| `lib.users`               | учётные записи       | PK `id`, UQ `username`, UQ `email`, `role`, `is_blocked`                                  |
| `lib.projects`            | проекты              | PK `id`, FK `owner_id → users.id` (RESTRICT)                                              |
| `lib.tasks`               | задачи               | PK `id`, FK `project_id → projects.id` (RESTRICT), FK `assignee_id → users.id` (SET NULL) |
| `lib.task_status_history` | аудит смены статусов | PK `id`, FK `task_id → tasks.id` (CASCADE)                                                |

Индексы: `users_username_key`, `users_email_key`, `projects_owner_id_idx`,
`tasks_project_id_status_idx`, `tasks_assignee_id_idx`.

Ограничения целостности (`db/03_constraints.sql`):

- `priority BETWEEN 1 AND 5`;
- `length(btrim(title)) > 0` для задач и проектов;
- формат email регулярным выражением;
- `username` 3–50 символов;
- запрет назначения заблокированного пользователя (проверка в приложении и в функции БД).

### 5.3. Статусная модель

```
NEW ──────► IN_PROGRESS ──────► DONE
 │                                ▲
 └────────────────────────────────┘
```

Разрешены только переходы вперёд: `NEW → IN_PROGRESS`, `NEW → DONE`,
`IN_PROGRESS → DONE`. Обратные переходы и любые изменения из `DONE` возвращают `400`.
Такое решение соответствует требованию ТЗ о контроле жизненного цикла и тест-кейсу
TC-05 (`NEW → DONE` допустим). Аудит переходов хранится в `task_status_history`.

## 6. REST API

Базовый URL: `http://localhost:3000`. Все защищённые запросы требуют
`Authorization: Bearer <JWT>`.

| Метод | Путь                              | Доступ     | Успех                          | Ошибки             |
| ----- | --------------------------------- | ---------- | ------------------------------ | ------------------ |
| GET   | `/health`                         | публичный  | 200 `{status:"ok"}`            | —                  |
| POST  | `/api/register`                   | публичный  | 201 `{token,user}`             | 400                |
| POST  | `/api/login`                      | публичный  | 200 `{token,user}`             | 400, 401, 403      |
| GET   | `/api/tasks?page=&limit=&status=` | USER/ADMIN | 200 `{items,total,page,limit}` | 400, 401           |
| POST  | `/api/tasks`                      | USER/ADMIN | 201 `Task`                     | 400, 401, 403, 404 |
| PATCH | `/api/tasks/:id/status`           | USER/ADMIN | 200 `Task`                     | 400, 401, 403, 404 |
| PATCH | `/api/tasks/:id/assign`           | USER/ADMIN | 200 `Task`                     | 400, 401, 403, 404 |
| GET   | `/api/tasks/overdue?projectId=`   | USER/ADMIN | 200 `Task[]`                   | 400, 401, 403, 404 |

Единый формат ошибок:

```json
{
  "error": "Validation failed",
  "issues": [{ "path": "title", "message": "String must contain at least 1 character(s)" }]
}
```

Коды: `400` — валидация/недопустимый переход, `401` — нет/просрочен токен,
`403` — нет прав/заблокирован, `404` — объект не найден, `500` — необработанная ошибка.

## 8. Архитектура

```
┌──────────────────────────┐        HTTP/JSON        ┌──────────────────────────┐
│  React SPA (Vite)        │ ──────────────────────► │  Express API             │
│  pages / components      │ ◄────────────────────── │  routes → controllers    │
│  api/http (JWT)          │                         │  middlewares (auth, zod) │
└──────────────────────────┘                         │  services (business)     │
                                                     └───────┬──────────┬───────┘
                                                             │          │
                                             ┌───────────────▼──┐   ┌───▼────────────────┐
                                             │ Prisma 7 + pg    │   │ Integrations       │
                                             │ adapter          │   │ weather / telegram │
                                             └───────┬──────────┘   └────────────────────┘
                                                     │
                                             ┌───────▼──────────┐
                                             │ PostgreSQL 15    │
                                             │ schema lib       │
                                             │ views, triggers  │
                                             └──────────────────┘
```

Слои сервера:

1. **routes** — маршрутизация и подключение middleware;
2. **controllers** — преобразование HTTP ↔ DTO, коды ответов;
3. **services** — бизнес-правила, права, переходы статусов, уведомления;
4. **integrations** — адаптеры внешних систем (axios, Telegram, консоль);
5. **config** — env-валидация и Prisma-клиент;
6. **middlewares** — аутентификация, валидация, централизованные ошибки.

## 10. Риски и допущения

| Риск                     | Вероятность | Влияние | Меры                                                                       |
| ------------------------ | ----------- | ------- | -------------------------------------------------------------------------- |
| Утечка JWT_SECRET        | Низкая      | Высокое | env, ротация, короткий TTL, не коммитить секреты                           |
| Брутфорс входа           | Средняя     | Среднее | bcrypt, единый текст ошибки; в prod — rate limit                           |
| Перегрузка БД отчётами   | Средняя     | Среднее | отдельная роль, индексы, лимиты, read-only                                 |
| Потеря данных            | Низкая      | Высокое | ежедневный дамп, проверка `pg_restore --list`, offsite-копия               |
| Сбой Telegram            | Средняя     | Низкое  | уведомление не блокирует бизнес-операцию                                   |
| Дрейф схемы Prisma ↔ SQL | Средняя     | Среднее | SQL-контур `taskflow_sql` отделён от Prisma-БД, миграции — источник истины |

Допущения: один экземпляр API; часовой пояс сервера UTC, отображение — локальное;
почтовые уведомления не отправляются; файлы не хранятся.
